## Confirmed cause

The bundled model manifest records `releaseValidatedMemoryGiB: [32]` for both
Qwen 3 models. `model_manager.rs` checks exact memory-class membership in both
model discovery and download preparation for release builds. Consequently,
non-32 GiB machines cannot even download the small model despite its 8 GiB
minimum-memory declaration. Apple's first screenshot shows this restriction;
the second shows the resulting empty engine selector.

This is not resolved by asking the reviewer to open Intelligence settings.
Do not add hardware classes to the validation list without physical evidence.
Do not present optional user-owned API credentials as a fix for the advertised
no-account local experience.

## Build 18 implementation

The user requested broad MacBook compatibility after this diagnosis. Build 18
replaces exact RAM-class membership with the model's declared minimum RAM:
8 GiB for Quick local and 16 GiB for the optional 8B model. Unknown memory fails
closed. The recorded physical-validation list remains unchanged. File hashes,
disk requirements, and the required device-local benchmark still apply.

First setup chooses the smallest compatible model. The empty engine picker
opens Intelligence settings, and unsupported subscription/local providers no
longer clutter the App Store provider list. Regression tests cover admission at
8, 16, 18, 24, 32, 36, 48, 64, 96, 128, 256, and 512 GiB; these are injected
capacity values, not physical hardware test results.

Intel support is not delivered by this change: the existing package, helper,
release tooling, and MLX runtime are arm64-only. A universal app plus a separately
validated Intel-compatible inference backend remains necessary for Intel Macs.

## Build 19 follow-up from native QA

Actual build 18 QA exposed two presentation bugs: pending provider discovery
briefly claimed no local provider existed, and App Store-blocked providers
still appeared because the UI only filtered `unsupported` distribution, while
the native contract uses `direct-only` plus `blocked-by-policy` status.

Build 19 adds explicit loading/error/retry states and publishes provider results
as soon as that probe resolves, independently of the other startup probes. It
filters both policy-blocked status and health without hiding usable Direct
providers. Renderer tests cover controlled pending -> failed -> retry -> model
installation available, with no blocked subscription tab or Ollama row.

Intel implementation remains separate: a candidate backend is
[llama.cpp](https://github.com/ggml-org/llama.cpp), which documents x86 CPU support.
[Tauri universal packaging](https://v2.tauri.app/distribute/macos-application-bundle/)
addresses the main binary, not compatibility of the current MLX helper. Neither
upstream support nor cross-compilation replaces physical Intel qualification.
